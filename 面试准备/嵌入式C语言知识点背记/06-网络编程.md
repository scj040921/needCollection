# 网络编程

## 分层、地址与字节序

- OSI 七层常作理论模型；TCP/IP 常用四层：应用、传输、网际、网络接口。HTTP 在应用层，TCP/UDP 在传输层，IP 在网际层。
- IP 地址定位主机，端口定位主机内进程；`IP:port` 才能唯一描述一个常见网络端点。
- 网络字节序为大端。发送前 `htons/htonl`，接收后 `ntohs/ntohl`；不要把结构体原样直接发到不同平台。

## TCP 与 UDP

| 项 | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接，三次握手建立 | 无连接 |
| 可靠性 | 有序、可靠字节流，重传/流控/拥塞控制 | 尽力交付，可能丢失、乱序、重复 |
| 边界 | **没有消息边界** | 保留单个报文边界 |
| 适用 | 登录、文件、控制指令 | 发现、实时音视频、可容错遥测 |

> [!warning] TCP 最大坑
> 一次 `recv` 不是一条业务消息；必须自定义协议边界，例如“固定头 + 长度 + 载荷”或明确分隔符并处理粘包/半包。

## TCP 服务器主流程

```text
socket → bind → listen → accept → recv/send → close
```

- `socket` 创建套接字；`bind` 绑定本地地址；`listen` 建立监听队列；`accept` 返回一个**新的已连接 fd**，监听 fd 继续接新连接。
- `connect` 用于客户端发起连接。阻塞 socket 上 `accept/recv` 可等待；非阻塞时常配合 `select/poll/epoll` 或事件循环。
- `send/write` 与 `recv/read` 都可能短传输；`recv == 0` 表示对端有序关闭。
- `SO_REUSEADDR` 常用于服务重启时复用本地地址；`SO_RCVLOWAT` 是接收低水位概念，实际可读性行为仍要结合 API/平台验证。

## TIME_WAIT 与健壮性

- 主动关闭 TCP 的一方进入 `TIME_WAIT`，目的是让旧报文消失并可靠完成终止；它通常不是错误。
- 应用层应有长度上限、超时、心跳/重连、错误码和版本字段。嵌入式端尤其要防止对端异常让接收缓冲无限增长。

## HTTP 与 JSON

- HTTP 请求：请求行（方法、路径、版本）+ 首部 + 空行 + 可选正文；响应：状态行 + 首部 + 空行 + 可选正文。
- `Content-Length` 或分块编码决定正文边界；HTTP 本身不是“收到一次就一定是一整包”。
- JSON 是文本数据格式：对象 `{}`、数组 `[]`、字符串、数字、布尔和 `null`。解析必须检查字段存在、类型、长度和范围，不能把网络输入直接当可信数据。

> [!question] 自测
> 为什么 UDP 不需要处理粘包？因为一次接收对应一个数据报；但若缓冲太小，数据报可能被截断，仍必须检查长度。

## 图片题目逐项补全

### 字节序与 TCP 连接/断开

- 发送网络数据必须统一字节序，否则小端主机直接把多字节整数写入网络，另一端会按相反顺序解释。字符串不做字节序转换，整数和协议长度字段要转换。
- TCP 建连：客户端 `SYN` → 服务端 `SYN+ACK` → 客户端 `ACK`。三次的核心是双方确认“收、发两个方向”均可工作，初始序号也被确认。
- TCP 正常关闭常为四次挥手：主动方 `FIN`，被动方 `ACK`，被动方处理完再 `FIN`，主动方 `ACK`；半关闭意味着一个方向不再发送，另一方向仍可接收。

### UDP、复用与超时

- 用信号驱动方式接收 UDP（如 `SIGIO`）会带来异步处理限制，工程中通常更易维护的是非阻塞 fd 配合 `select/poll/epoll`，或专门接收线程。
- 多路复用服务器由一个事件循环同时监视多个 fd；`select` 有 fd 数量限制且每轮重置集合，`poll` 无该位图限制，`epoll` 适合大量连接的就绪通知。
- `SO_RCVTIMEO/SO_SNDTIMEO` 可让阻塞收发在超时后返回错误（常见 `EAGAIN/EWOULDBLOCK`）；应用还需定义重试、断线与业务超时策略。
- `SO_REUSEPORT` 允许多个 socket 绑定同一地址端口（需平台支持），常用于多进程/多线程分摊新连接；它与 `SO_REUSEADDR` 的语义不同，不能混淆。

### HTTP/JSON 的解析安全

- HTTP 先解析起始行和首部，再依据 `Content-Length` 或 chunked 规则收集正文；设置最大首部/正文长度、读取超时和连接数上限，防止恶意输入耗尽内存。
- JSON 解析后仍要做业务校验：字段是否缺失、数字是否溢出、字符串是否超长、未知字段如何兼容；解析成功不等于数据可信。
